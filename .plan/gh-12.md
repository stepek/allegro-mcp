## 0. Research findings (validated, not guesswork)

These were confirmed by reading the vendored `rmcp-3.2.0` source
(`~/.cargo/registry/src/.../rmcp-3.2.0`) and by compiling a throwaway
scratch crate (`/tmp/opencode/rmcp-http-scratch`) against the real
`Cargo.lock`-pinned `rmcp = "3.2.0"` — it built cleanly with `cargo build`.

1. **Feature flag**: `transport-streamable-http-server` is the correct rmcp
   feature. It transitively enables `transport-streamable-http-server-session`,
   `server-side-http`, `transport-worker`, `tower` (→ `tower-service`), `uuid`,
   `sse-stream`, `http`, `http-body`, `http-body-util`, `bytes`, `rand`,
   `tokio-stream`, `base64`. No other rmcp feature is needed for the server
   side (client-side streamable-http features are irrelevant here).
2. **axum version**: `axum = "0.8"` (resolves to `0.8.9` in this graph,
   consistent with `http = "1.5"`, `tower = "0.5.3"`, `tower-service = "0.3.3"`
   already implied by `reqwest 0.12`). `default-features = false` with
   `features = ["http1", "json", "tokio"]` is sufficient — verified by the
   scratch build (no missing-symbol / missing-feature errors).
3. **Integration shape**: `rmcp::transport::streamable_http_server::tower::StreamableHttpService`
   implements `tower_service::Service<http::Request<B>>` for any
   `S: rmcp::ServerHandler + Send + 'static` and `M: SessionManager`. It plugs
   straight into `axum::Router::nest_service("/mcp", service)` — no adapter
   code needed. Re-exported at `rmcp::transport::{StreamableHttpService, StreamableHttpServerConfig}`
   and `rmcp::transport::streamable_http_server::session::local::LocalSessionManager`.
4. **Service factory is per-connection, not per-process**: `StreamableHttpService::new`
   takes `impl Fn() -> Result<S, io::Error> + Send + Sync + 'static`. Our
   `AllegroServer` must be cheaply `Clone` (all fields are already `Arc<..>`,
   `reqwest::Client` (Clone), `bool`, `Option<String>` — trivial derive).
5. **DNS-rebinding guard**: `StreamableHttpServerConfig::allowed_hosts`
   defaults to `["localhost", "127.0.0.1", "::1"]` (confirmed:
   `rmcp-3.2.0/src/transport/streamable_http_server/tower.rs:172`,
   `impl Default for StreamableHttpServerConfig`). Behind a Docker network
   or reverse proxy, the inbound `Host` header will be something else (e.g.
   `allegro-mcp:8080`, or the reverse-proxy's public hostname), so the
   default would reject every real request with `403 Forbidden`. This must
   be made configurable (Phase 3).

   **Empty-vec semantic — verified against the vendored source, not
   guesswork.** Read directly from `tower.rs:762-777`:

   ```rust
   fn host_is_allowed(host: &NormalizedAuthority, allowed_hosts: &[String]) -> bool {
       if allowed_hosts.is_empty() {
           // If the allowed hosts list is empty, allow all hosts (not recommended).
           return true;
       }
       allowed_hosts
           .iter()
           .filter_map(|allowed| parse_allowed_authority(allowed))
           .any(|allowed| {
               allowed.host == host.host
                   && match allowed.port {
                       Some(port) => host.port == Some(port),
                       None => true,
                   }
           })
   }
   ```

   **Confirmed: `allowed_hosts.is_empty() == true` ⇒ every `Host` header
   is accepted (allow-all).** This is exactly rmcp's own built-in
   "disable the check" path — `tower.rs:189-193`:

   ```rust
   /// Disable allowed hosts. This will allow requests with any `Host` header, which is NOT recommended for public deployments.
   pub fn disable_allowed_hosts(mut self) -> Self {
       self.allowed_hosts.clear();
       self
   }
   ```

   So `resolve_allowed_hosts()` returning `Vec::new()` for the `*` case
   (Phase 3.4) and feeding it through `.with_allowed_hosts(Vec::new())` is
   *functionally identical* to calling `.disable_allowed_hosts()` —
   verified, not assumed. The builder method name is also confirmed
   exactly as `with_allowed_hosts` (`tower.rs:182-188`, note the plural
   `hosts` and the `with_` prefix — not `set_allowed_hosts` or similar):

   ```rust
   pub fn with_allowed_hosts(
       mut self,
       allowed_hosts: impl IntoIterator<Item = impl Into<String>>,
   ) -> Self {
       self.allowed_hosts = allowed_hosts.into_iter().map(Into::into).collect();
       self
   }
   ```

   Implementer's choice for the `*` branch: either keep
   `resolve_allowed_hosts() -> Vec<String>` feeding `.with_allowed_hosts(...)`
   uniformly for every branch (simplest — one code path, what Phase 3.4
   does), or special-case `*` to call `.disable_allowed_hosts()` directly
   for self-documenting clarity at the call site. Both are verified
   correct and equivalent; Phase 3.4 keeps the uniform `Vec<String>`
   version and documents the equivalence inline.
6. **CA certs are a non-issue**: `reqwest`'s `rustls-tls` feature (already
   used in this project, see `Cargo.toml` line 27) bundles Mozilla's root
   store via `webpki-roots` at compile time — it does **not** read
   `/etc/ssl/certs`. Distroless base images need no CA-cert handling for
   outbound HTTPS (Allegro API / OAuth / schema fetch) to keep working.
7. **No shell in distroless** → Docker `HEALTHCHECK CMD` cannot run
   `curl`/`wget`. Solution: add a tiny `allegro-mcp healthcheck` CLI
   subcommand that does a local `GET /health` with a 2 s timeout and maps
   the result to a process exit code. This is the standard pattern for
   distroless Rust images.

### Discrepancy to flag explicitly: "device-flow banner"

The issue's task 7 says *"Device-flow banner in logs"*. **This codebase does
not implement a device-authorization flow.** `src/auth/mod.rs` only
implements OAuth2 `client_credentials` (app-level token, no user consent
step), and `src/config.rs` explicitly **rejects** `auth_flow = "device_code"`
as unsupported (see `config.rs` test
`from_toml_str_unknown_auth_flow_errors_listing_supported_values`). There is
no user-facing "enter this code at allegro.pl/…" step to bannerize.

Given that, Phase 3 implements the closest honest equivalent: an **eager
startup token-fetch health check** (the server calls `AllegroAuth::token()`
once during HTTP-mode startup, before it starts accepting connections) with
a prominent success/failure log banner, plus a live `/auth/status` endpoint.
This gives the admin-visibility value the issue is after (dead credentials
show up immediately in `docker logs`, not on the first tool call) without
inventing a flow that doesn't exist. `docs/open-webui.md` documents this
plainly and the re-auth procedure (rotate env vars + restart container,
since no token is persisted to disk today). If a future phase adds a real
device-authorization flow, `/auth/status` and the startup banner are the
natural extension points.

### 2.4 `main()` — dispatch `Healthcheck` before any config/network setup

Insert right after `let cli = Cli::parse();` / tracing init, **before**
`config::Config::load(...)`, so the probe stays fast and doesn't require
Allegro credentials to be present:

```rust
if matches!(cli.command, Some(Commands::Healthcheck)) {
    return run_healthcheck().await;
}
```

**Match-exhaustiveness note (easy to miss):** this early-return happens
*before* `main()`'s existing `match cli.command { Some(Commands::Schema {..}) => ..., Some(Commands::Tools {..}) => ..., None => ... }` block
(2.5 below). Rust's exhaustiveness checker has no notion of "already
handled earlier via an `if` + early return" — it only sees the static
shape of the `Commands` enum at the `match` site. Since `Commands` now
has three variants (`Schema`, `Tools`, `Healthcheck`), that later `match`
becomes **non-exhaustive and fails to compile** unless it also covers
`Commands::Healthcheck`. Add an explicit arm:

```rust
match cli.command {
    Some(Commands::Schema { action: SchemaAction::Stats }) => { /* unchanged */ }
    Some(Commands::Tools { action: ToolsAction::List }) => { /* unchanged */ }
    Some(Commands::Healthcheck) => {
        // Unreachable: handled by the early return above, before config
        // loading / network setup. Kept as an explicit arm (rather than
        // a wildcard `_ =>`) so adding a future `Commands` variant here
        // forces a compile error instead of silently falling through.
        unreachable!("Commands::Healthcheck is handled by the early return in main()")
    }
    None => { /* see 2.5 */ }
}
```

The early-return-then-`unreachable!()` pairing is the pattern to use
here — do **not** collapse `Healthcheck` handling into the main `match`
arm instead of the early return, since the whole point of the early
return is to skip `config::Config::load(...)` and client construction
(2.4's docstring: "stays fast and doesn't require Allegro credentials to
be present").

New function (near the bottom, alongside `run_mcp_server`):

```rust
/// Docker `HEALTHCHECK` probe: `GET http://127.0.0.1:$PORT/health` with a
/// short timeout. Reads the same `$PORT` (default 8080) the HTTP server
/// binds to. Exits non-zero (via `anyhow::Error`) on any failure — timeout,
/// connection refused, or non-2xx status — which Docker treats as unhealthy.
async fn run_healthcheck() -> Result<()> {
    let port = std::env::var("PORT")
        .ok()
        .and_then(|v| v.parse::<u16>().ok())
        .unwrap_or(8080);
    let url = format!("http://127.0.0.1:{port}/health");

    let client = reqwest::Client::builder()
        .timeout(std::time::Duration::from_secs(2))
        .build()?;
    let resp = client.get(&url).send().await?;

    if resp.status().is_success() {
        Ok(())
    } else {
        anyhow::bail!("healthcheck failed: HTTP {}", resp.status());
    }
}
```

### 3.0 `src/main.rs` — extract shared server-build logic (`build_allegro_server`)

**Do this before 3.4.** Today's `run_mcp_server` (existing code, unchanged
shape) reads `ALLEGRO_CLIENT_ID`/`ALLEGRO_CLIENT_SECRET`, builds
`AllegroAuth`, loads the schema, builds the `ToolRegistry`, and wires up
`AllegroServer`. The new HTTP transport needs to do the **exact same
sequence** before it can start serving `/mcp`. Without extraction, that
whole block gets copy-pasted into `http_server::run_http_server` — two
copies of env-var parsing, error messages, and construction order to keep
in sync forever. Extract it once, in `main.rs`, as:

```rust
/// Shared server-build logic for both transports: reads
/// `ALLEGRO_CLIENT_ID`/`ALLEGRO_CLIENT_SECRET`, builds `AllegroAuth`,
/// loads the schema, builds the tool registry, and wires up the
/// `AllegroServer` handler. Transport-specific code (`run_mcp_server`'s
/// stdio serve loop; `http_server::run_http_server`'s axum router +
/// eager auth-check banner) picks up from the returned handler.
async fn build_allegro_server(
    cfg: &config::Config,
    api_client: reqwest::Client,
    schema_client: &reqwest::Client,
    source: &schema::SchemaSource,
) -> Result<server::AllegroServer> {
    let client_id = std::env::var("ALLEGRO_CLIENT_ID")
        .map_err(|_| anyhow::anyhow!("missing environment variable: ALLEGRO_CLIENT_ID"))?;
    let client_secret = std::env::var("ALLEGRO_CLIENT_SECRET")
        .map_err(|_| anyhow::anyhow!("missing environment variable: ALLEGRO_CLIENT_SECRET"))?;

    let auth = auth::AllegroAuth::with_http_client(
        client_id,
        client_secret,
        config::auth_base_url(cfg.sandbox).to_owned(),
        api_client.clone(),
    )
    .with_scopes(cfg.scopes.clone());

    let (api, _raw) = schema::load_with_client(schema_client, source)
        .await
        .map_err(|e| anyhow::anyhow!("schema load failed: {e}"))?;
    let registry = tool_registry::ToolRegistry::from_openapi(&api)
        .map_err(|e| anyhow::anyhow!("registry build failed: {e}"))?;
    tracing::info!(tool_count = registry.len(), "tool registry built");

    Ok(server::AllegroServer::new(registry, auth, cfg.sandbox).with_http_client(api_client))
}
```

`run_mcp_server` shrinks to:

```rust
async fn run_mcp_server(
    cfg: config::Config,
    api_client: reqwest::Client,
    schema_client: reqwest::Client,
    source: schema::SchemaSource,
) -> Result<()> {
    tracing::info!(sandbox = cfg.sandbox, "starting MCP server (stdio transport)");

    let handler = build_allegro_server(&cfg, api_client, &schema_client, &source).await?;

    let transport = rmcp::transport::io::stdio();
    let running = rmcp::serve_server(handler, transport)
        .await
        .map_err(|e| anyhow::anyhow!("MCP server init failed: {e}"))?;
    tracing::info!("MCP server ready");
    if let Err(e) = running.waiting().await {
        tracing::warn!("MCP server exited with error: {e}");
    }
    tracing::info!("MCP server shut down");
    Ok(())
}
```

**Why the helper stays physically in `main.rs` and `http_server.rs` never
calls it directly (important, easy to get wrong):** this crate has
*separate* `[[bin]]` (`src/main.rs`) and `[lib]` (`src/lib.rs`,
`name = "allegro_mcp"`) targets (`Cargo.toml` lines 11-17). `main.rs`
declares its own private `mod http_server;` (2.1) and `lib.rs` separately
declares `pub mod http_server;` (3.1) — **the same `src/http_server.rs`
source file gets compiled twice, once under each crate root.** A
function defined only in `main.rs` (like `build_allegro_server`) does
**not** exist under `crate::` when `http_server.rs` is compiled as part
of the `allegro_mcp` *library* target (needed so
`tests/http_server_integration.rs` can `use allegro_mcp::http_server::...`,
per 3.5) — `crate::build_allegro_server` would be a compile error in that
target even though it works fine in the `allegro-mcp` *binary* target.

So `http_server::run_http_server` must **not** build its own
`AllegroServer` by calling back into `main.rs`. Instead, `main.rs`'s
dispatch code (2.5) builds the handler via `build_allegro_server` and
passes the **already-built** `AllegroServer` into `run_http_server`,
which only owns transport-specific concerns (eager auth-check banner,
router, bind/serve). This also directly satisfies 3.5's requirement that
`run_http_server`'s signature stay simple and that router construction
be independently testable — see the revised 3.4/3.5 below.

### 3.3 `src/auth/mod.rs` — `AuthStatus` + `AllegroAuth::status()`

Add near the bottom of the `impl AllegroAuth` block (after `fetch_token`):

```rust
/// A point-in-time snapshot of the token cache, for the `/auth/status`
/// HTTP endpoint (admin visibility — see `src/http_server.rs`). Never
/// exposes the token itself.
#[derive(Debug, Clone, serde::Serialize)]
pub struct AuthStatus {
    /// Always `"client_credentials"` today — this crate does not
    /// implement a device-authorization / user-consent flow yet.
    pub auth_flow: &'static str,
    /// `true` once at least one token fetch has succeeded since process
    /// start (the in-memory cache is never persisted to disk today).
    pub token_cached: bool,
    /// `true` when the cached token still has > 60 s remaining (the same
    /// threshold `token()` uses to decide whether to refresh).
    pub token_valid: bool,
    /// Seconds remaining before expiry, if a token is cached.
    pub expires_in_secs: Option<u64>,
}

/// Returns a snapshot of the current token-cache state without
/// triggering a fetch or refresh — a read-only status check, safe to call
/// from an unauthenticated-by-default endpoint (it reveals cache
/// freshness, never the token itself).
pub async fn status(&self) -> AuthStatus {
    let guard = self.cache.read().await;
    match guard.as_ref() {
        Some(cached) => AuthStatus {
            auth_flow: "client_credentials",
            token_cached: true,
            token_valid: cached.is_valid(),
            expires_in_secs: cached
                .expires_at
                .checked_duration_since(Instant::now())
                .map(|d| d.as_secs()),
        },
        None => AuthStatus {
            auth_flow: "client_credentials",
            token_cached: false,
            token_valid: false,
            expires_in_secs: None,
        },
    }
}
```

```rust
//! module only owns transport-specific concerns: the eager startup
//! auth-check banner, the axum router/middleware wiring
//! ([`build_router`]), and binding/serving.
//!
//! Exposes three routes:
//! - `POST/GET/DELETE /mcp`  — the MCP Streamable HTTP endpoint (rmcp).
//! - `GET /health`           — unauthenticated liveness probe (Docker
//!                             HEALTHCHECK, load balancers).
//! - `GET /auth/status`      — admin visibility into the Allegro token
//!                             cache (see `crate::auth::AuthStatus`).
//!
//! `/mcp` and `/auth/status` are gated behind an optional static bearer
//! token (`ALLEGRO_MCP_SERVER_TOKEN`) — off by default, reverse-proxy
//! friendly. `/health` is always public (health checks must not need
//! credentials).

use std::net::{IpAddr, Ipv4Addr, SocketAddr};
use std::sync::Arc;

use anyhow::Result;
use axum::extract::{Request, State};
use axum::http::{header::AUTHORIZATION, StatusCode};
use axum::middleware::{self, Next};
use axum::response::{IntoResponse, Response};
use axum::routing::get;
use axum::{Json, Router};
use rmcp::transport::streamable_http_server::session::local::LocalSessionManager;
use rmcp::transport::{StreamableHttpServerConfig, StreamableHttpService};
use tracing::{error, info, warn};

/// Env var enabling the optional static bearer-token guard. Off by
/// default — this server is designed to sit behind a reverse proxy /
/// Docker-internal network (Open WebUI talking to `allegro-mcp:8080` on a
/// private compose network) where TLS + access control is handled
/// upstream. Set this to require `Authorization: Bearer <token>` on
/// `/mcp` and `/auth/status`.
const SERVER_TOKEN_ENV: &str = "ALLEGRO_MCP_SERVER_TOKEN";

/// Comma-separated `host` / `host:port` allow-list for the Streamable HTTP
/// transport's DNS-rebinding guard. Defaults to loopback-only (rmcp's
/// default), which rejects every request arriving via a Docker service
/// name or reverse-proxy hostname. Set this to the hostname(s) clients
/// actually use, e.g. `allegro-mcp,allegro-mcp:8080` on a compose network,
/// or your public reverse-proxy hostname. Set to `*` to disable the check
/// entirely (not recommended for public deployments — see SECURITY.md).
const ALLOWED_HOSTS_ENV: &str = "ALLEGRO_MCP_ALLOWED_HOSTS";

#[derive(Clone)]
pub struct AppState {
    auth: Arc<AllegroAuth>,
    server_token: Option<Arc<str>>,
}

impl AppState {
    /// Constructs the shared HTTP-transport state.
    ///
    /// `#[doc(hidden)]` — internal wiring for `run_http_server` /
    /// [`build_router`], exposed only so
    /// `tests/http_server_integration.rs` can build a router directly
    /// (Phase 3.5's mandated design: exercise routing/middleware without
    /// going through `run_http_server`'s env-var-driven startup).
    #[doc(hidden)]
    pub fn new(auth: Arc<AllegroAuth>, server_token: Option<Arc<str>>) -> Self {
        Self { auth, server_token }
    }
}

/// Runs the MCP server over Streamable HTTP on an already-built
/// `handler` (see `main.rs::build_allegro_server`, Phase 3.0): runs the
/// eager startup auth-check banner, builds the router ([`build_router`]),
/// then binds and serves `/mcp`, `/health`, and `/auth/status` on
/// `0.0.0.0:{port}` until the process is signalled to stop.
///
/// Takes an already-built `handler` (not `cfg`/`api_client`/
/// `schema_client`/`source`) rather than duplicating
/// `build_allegro_server`'s auth/schema/registry construction — this
/// module never references `main.rs` directly (it can't: `main.rs` and
/// `lib.rs` are separate crate roots that both compile this file, see
/// Phase 3.0's rationale), so the caller in `main.rs` builds the handler
/// first and hands it over.
pub async fn run_http_server(
    handler: crate::server::AllegroServer,
    sandbox: bool,
    port: u16,
) -> Result<()> {
    info!(port, sandbox, "starting MCP server (Streamable HTTP transport)");

    let auth_handle = handler.auth_handle();

    // See the module doc's "Discrepancy" note in the plan: no device-flow
    // exists, so this eager fetch + banner is the closest honest
    // equivalent to "first-run auth UX" — a broken client_id/secret pair
    // is caught at startup (visible in `docker logs`) instead of silently
    // failing on the first tool call from Open WebUI.
    match auth_handle.token().await {
        Ok(_) => info!(
            "=================================================================\n \
             allegro-mcp: Allegro OAuth2 client_credentials check OK (sandbox={})\n \
             ================================================================",
            sandbox
        ),
        Err(e) => {
            error!(
                "=================================================================\n \
                 allegro-mcp: STARTUP AUTH CHECK FAILED: {e}\n \
                 Check ALLEGRO_CLIENT_ID / ALLEGRO_CLIENT_SECRET and retry.\n \
                 =================================================================",
            );
            anyhow::bail!("startup Allegro auth check failed: {e}");
        }
    }

    let server_token = std::env::var(SERVER_TOKEN_ENV).ok().map(Arc::from);
    if server_token.is_some() {
        info!("bearer token auth ENABLED for /mcp and /auth/status");
    } else {
        warn!(
            "bearer token auth DISABLED (set {SERVER_TOKEN_ENV} to enable) — \
             relying on network isolation / reverse proxy for access control"
        );
    }

    let allowed_hosts = resolve_allowed_hosts();
    let mcp_service: StreamableHttpService<crate::server::AllegroServer, LocalSessionManager> =
        StreamableHttpService::new(
            move || Ok(handler.clone()),
            Arc::new(LocalSessionManager::default()),
            StreamableHttpServerConfig::default().with_allowed_hosts(allowed_hosts),
        );

    let state = AppState::new(auth_handle, server_token);
    let app = build_router(state, mcp_service);

    let addr = SocketAddr::new(IpAddr::V4(Ipv4Addr::UNSPECIFIED), port);
    let listener = tokio::net::TcpListener::bind(addr)
        .await
        .map_err(|e| anyhow::anyhow!("failed to bind {addr}: {e}"))?;
    info!(%addr, "MCP server ready, serving /mcp, /health, /auth/status");

    axum::serve(listener, app)
        .await
        .map_err(|e| anyhow::anyhow!("HTTP server error: {e}"))?;

    info!("MCP server shut down");
    Ok(())
}

/// Builds the axum [`Router`]: `/health` (always public, added *after*
/// the merge so the bearer-auth `route_layer` never touches it) merged
/// with the bearer-auth-gated `/mcp` + `/auth/status` routes.
///
/// **Required extraction, not optional** (Phase 3.5): split out from
/// `run_http_server` specifically so
/// `tests/http_server_integration.rs` can construct a real router —
/// bearer-auth middleware, `/health`, `/auth/status`, and a real `/mcp`
/// `StreamableHttpService` — and drive it over real HTTP on an ephemeral
/// port, without going through `run_http_server`'s env-var-driven
/// `ALLEGRO_CLIENT_ID`/`ALLEGRO_CLIENT_SECRET` lookup or the eager
/// startup auth-check network call.
#[doc(hidden)]
pub fn build_router(
    state: AppState,
    mcp_service: StreamableHttpService<crate::server::AllegroServer, LocalSessionManager>,
) -> Router {
    let protected = Router::new()
        .nest_service("/mcp", mcp_service)
        .route("/auth/status", get(auth_status_handler))
        .route_layer(middleware::from_fn_with_state(state.clone(), bearer_auth));

    Router::new()
        .route("/health", get(health_handler))
        .merge(protected)
        .with_state(state)
}

/// Parses [`ALLOWED_HOSTS_ENV`] into rmcp's allow-list format. Absent env
/// var ⇒ rmcp's loopback-only default (safe default for `docker run -p`
/// local testing); `*` ⇒ disabled (documented tradeoff, see
/// SECURITY.md); otherwise the comma-separated list verbatim (each entry
/// may be `host` or `host:port`, matching `StreamableHttpServerConfig`'s
/// own format).
fn resolve_allowed_hosts() -> Vec<String> {
    match std::env::var(ALLOWED_HOSTS_ENV) {
        Ok(v) if v.trim() == "*" => {
            warn!(
                "{ALLOWED_HOSTS_ENV}=* — Host-header DNS-rebinding protection DISABLED"
            );
            Vec::new() // empty allow-list == rmcp "allow all" (see tower.rs host_is_allowed)
        }
        Ok(v) => v
            .split(',')
            .map(str::trim)
            .filter(|s| !s.is_empty())
            .map(str::to_owned)
            .collect(),
        Err(_) => vec!["localhost".into(), "127.0.0.1".into(), "::1".into()],
    }
}

async fn health_handler() -> impl IntoResponse {
    (StatusCode::OK, "ok")
}

async fn auth_status_handler(State(state): State<AppState>) -> impl IntoResponse {
    Json(state.auth.status().await)
}

/// Optional static bearer-token guard. No-op (passes every request
/// through) when `ALLEGRO_MCP_SERVER_TOKEN` was not set at startup.
async fn bearer_auth(State(state): State<AppState>, req: Request, next: Next) -> Response {
    let Some(expected) = &state.server_token else {
        return next.run(req).await;
    };

    let provided = req
        .headers()
        .get(AUTHORIZATION)
        .and_then(|v| v.to_str().ok())
        .and_then(|v| v.strip_prefix("Bearer "));

    match provided {
        Some(token) if constant_time_eq(token.as_bytes(), expected.as_bytes()) => {
            next.run(req).await
        }
        _ => (StatusCode::UNAUTHORIZED, "unauthorized").into_response(),
    }
}

/// Constant-time byte comparison — avoids a timing side-channel on the
/// bearer-token check. No new dependency: this is a ~5-line primitive,
/// not worth pulling in `subtle`/`constant_time_eq` for.
fn constant_time_eq(a: &[u8], b: &[u8]) -> bool {
    if a.len() != b.len() {
        return false;
    }
    a.iter().zip(b).fold(0u8, |acc, (x, y)| acc | (x ^ y)) == 0
}

#[cfg(test)]
mod tests {

    #[test]

        assert!(constant_time_eq(b"secret", b"secret"));
    }

    #[test]
    fn constant_time_eq_rejects_different_slices() {
        assert!(!constant_time_eq(b"secret", b"wrong-token"));
    }

    #[test]
```

**Design notes for the implementer:**

- `build_router` is a **required** extraction, not a nice-to-have — see
  3.5, which mandates driving it directly from the integration test.
  `run_http_server` calling `build_router(state, mcp_service)` instead of
  inlining the `protected`/`app` construction is not optional scope.
- `route_layer` (not `layer`) is deliberate: it applies the bearer-auth
  middleware only to the routes already registered on `protected`
  (`/mcp`, `/auth/status`), not to routes merged in afterwards. `/health`
  is added to the returned router *after* the merge, so it is never
  touched by the middleware and stays always-public. This was verified in
  the scratch build.
- `resolve_allowed_hosts()` returning `Vec::new()` for `*` relies on
  `rmcp`'s own `host_is_allowed` treating an empty `allowed_hosts` list as
  "allow all" — verified against the vendored source with the exact code
  quoted in Section 0 (not a guess): `host_is_allowed`'s
  `if allowed_hosts.is_empty() { return true; }` is literally the body of
  `disable_allowed_hosts()`'s effect. `with_allowed_hosts` (confirmed
  exact name, `tower.rs:182`) is the only builder method needed since
  passing it an empty vec is equivalent to `disable_allowed_hosts()`;
  either works, empty-vec keeps `resolve_allowed_hosts()` a straight
  `Vec<String>` return with one call site.
- The eager `auth_handle.token().await` call at startup means the very
  first Allegro credential validation happens before the port is bound —
  a bad `ALLEGRO_CLIENT_SECRET` fails the container immediately
  (`docker-compose` / k8s will show a crash-loop, which is the correct
  failure mode for a misconfigured deployment) rather than accepting
  connections and failing tool calls later.

### 3.5 Integration test: `tests/http_server_integration.rs` (new)

**Requirement, not a choice.** `run_http_server` (as of 3.0/3.4) no longer
reads `ALLEGRO_CLIENT_ID`/`ALLEGRO_CLIENT_SECRET` or builds its own
`AllegroAuth` itself — the caller (`main.rs::build_allegro_server`) does
that, pointed at `crate::config::auth_base_url(sandbox)`, which is not
overridable to a wiremock URL. Driving this test through the full
`run_http_server` entry point would therefore mean making real network
calls to `allegro.pl` from CI, which is a non-starter. So this test
**must** target [`build_router`] directly (3.4) — that is a mandated part
of Phase 3's design, not an optional "option (b)"; `build_router`'s
extraction happens in 3.4 specifically so this test can exist without
touching real Allegro infrastructure.

Follows the existing integration-test conventions (`tests/mcp_server_integration.rs`
uses `allegro_mcp::...` public API + `fixtures/allegro_sample.yaml`; this one
additionally needs `wiremock` for the OAuth token endpoint, same as other
integration tests in this repo). Binds to `127.0.0.1:0` (ephemeral port) so
tests never collide.


**Test steps**, using `build_router` (mirrors `mcp_server_integration.rs`'s
`build_registry()` helper for the schema/registry half):

1. Load `fixtures/allegro_sample.yaml` into an `openapiv3::OpenAPI` and
   build a `ToolRegistry::from_openapi(&api)` (same fixture/helper
   `mcp_server_integration.rs` already uses).
2. Start `mock_token_server()`, build
   `AllegroAuth::with_base_url("id".into(), "secret".into(), mock.uri())`.
3. Build `AllegroServer::new(registry, auth, false)` and a
   `StreamableHttpService` from it (same construction as
   `run_http_server`'s, minus the eager auth-check call — that's
   deliberately skipped so this test controls exactly when/if the mock
   token endpoint gets hit).
4. Build `AppState::new(server.auth_handle(), server_token)` — once with
   `server_token: None`, once with `server_token: Some(Arc::from("secret"))`
   — and call `build_router(state, mcp_service)` for each case.
5. Bind `TcpListener::bind("127.0.0.1:0")`, spawn `axum::serve(...)` in a
   `tokio::spawn`, drive it with `reqwest::Client`.
6. Assert:
   - `GET /health` → `200 "ok"`, **no** `Authorization` header needed,
     even when `server_token` is `Some(...)` (proves `/health` is outside

   - `GET /auth/status` with `server_token: None` → `200`, JSON body has

   - With `server_token: Some("secret".into())`: `GET /auth/status`
     without `Authorization` → `401`; with `Authorization: Bearer secret`
     → `200`; with `Authorization: Bearer wrong` → `401`.
   - `POST /mcp` with a JSON-RPC `initialize` body → `200`/`text/event-stream`
     (mirrors the `initialize()` helper in `mcp_server_integration.rs`,
     just over `reqwest::Client::post(...)` instead of the duplex stream).

**File**: `/home/stepek/reps/allegro-mcp/12/docs/open-webui.md` (new)

Grounded in Open WebUI's own docs (`docs.openwebui.com/features/extensibility/mcp/`,
fetched during planning — requires **Open WebUI v0.6.31+** for native
Streamable HTTP MCP support). Content outline (write in full prose, not
just headings):

1. **Prerequisites**
   - Open WebUI ≥ v0.6.31 (native MCP support; earlier versions need the
     `mcpo` stdio/SSE→OpenAPI bridge instead — link
     https://github.com/open-webui/mcpo — and this server's `--stdio`
     flag would be the target for that bridge, not the HTTP transport).
   - `allegro-mcp` running and reachable from the Open WebUI container
     (same compose network, or `host.docker.internal:8080` if Open WebUI
     is Docker and `allegro-mcp` runs on the host — Open WebUI's own docs
     call this out explicitly for `localhost` URLs).
   - `ALLEGRO_CLIENT_ID`/`ALLEGRO_CLIENT_SECRET` set and the startup auth
     banner showing `OK` in `docker logs allegro-mcp` (see Phase 3).

2. **Add the connection** (mirrors Open WebUI's own quick-start, adapted):
   1. **Settings → Admin → Integrations**.
   2. Under **External Tool Servers**, click **+ Add Connection**.
   3. Set **Type** to **MCP (Streamable HTTP)** — *not* "OpenAPI"; picking
      the wrong type causes Open WebUI's UI to hang on an infinite loading
      screen (their own documented gotcha).
   4. **Server URL**: `http://allegro-mcp:8080/mcp` (compose network name)
      or `http://host.docker.internal:8080/mcp` (host-run allegro-mcp).
   5. **Auth**:
      - `None` if `ALLEGRO_MCP_SERVER_TOKEN` is unset on the server.
      - `Bearer`, with **Key** = the same value as
        `ALLEGRO_MCP_SERVER_TOKEN`, if the bearer guard is enabled.
        **Do not** pick `Bearer` with an empty key — Open WebUI sends a
        bare `Authorization: Bearer` header in that case, which this
        server's middleware (and most servers) reject outright.
   6. **Save**.
   3. MCP connections in Open WebUI are **admin-only** by design — regular
      users cannot self-register one; grant tool access via **Access
      Control** scoping on the connection instead.

3. **Streamable HTTP vs SSE — quirks to know**
   - Open WebUI's native MCP client speaks **Streamable HTTP only** (no
     native stdio/legacy-SSE support) — this is exactly the transport
     `allegro-mcp` implements by default (no `--stdio`), so no bridge is
     needed for this integration.
   - If you ever need to expose a *stdio*-only MCP server (e.g. running
     `allegro-mcp --stdio` for local testing) to Open WebUI, use `mcpo`
     as a translation layer — do not try to point Open WebUI's MCP
     connection type at a stdio process directly, it will not work.
   - `allegro-mcp`'s Streamable HTTP transport defaults to
     **legacy session mode** (rmcp `StreamableHttpServerConfig::legacy_session_mode = true`),
     i.e. it issues an `Mcp-Session-Id` on `initialize` and expects it on
     subsequent requests — this is what Open WebUI's client already does,
     no configuration needed on either side.
   - Cold starts: this server loads the full Allegro OpenAPI schema and
     builds the tool registry (~200 tools) once at startup, before the
     port is bound. If Open WebUI's `session.initialize()` handshake
     times out against a slow/cold container, raise Open WebUI's
     `MCP_INITIALIZE_TIMEOUT` (default 10 s) rather than assuming the
     server is broken.

4. **Verifying the connection** — after saving, open a chat, click
   **+ → Integrations → Tools**, and confirm `allegro-mcp` tools are
   listed (there will be many — mention the tool-count guard /
   allow-deny filters from `src/config.rs`'s `ToolFilters` as the knob to
   reach for if the list is unwieldy for a given model).

5. **Re-auth procedure** — since this server does not persist tokens to
   disk today (Section 0's "Discrepancy" note), rotating
   `ALLEGRO_CLIENT_SECRET` (e.g. after a leak, or Allegro-side rotation)
   is: update the env var (compose `.env` / `ALLEGRO_MCP_SERVER_TOKEN`
   secret store) and `docker compose up -d --force-recreate allegro-mcp`
   — the fresh process re-runs the startup auth check against the new
   credentials. No manual token-file cleanup is needed (nothing is
   cached on disk).

6. **Troubleshooting** — link back to `SECURITY.md`, and note the
   `/auth/status` endpoint (`curl -H "Authorization: Bearer $TOKEN" http://allegro-mcp:8080/auth/status`
   if the bearer guard is on) as the first thing to check when tool calls
   fail with auth-shaped errors from the Allegro API side.

## Phase 8: `SECURITY.md` — PENDING

**File**: `/home/stepek/reps/allegro-mcp/12/SECURITY.md` (new)

Content outline:

1. **Threat model for this deployment mode** — `allegro-mcp` in HTTP mode
   holds a live Allegro `client_credentials` token capable of acting on
   the linked Allegro account/app (read and, depending on requested
   scopes, write access — offers, orders, etc., per `cfg.scopes`).
   Anyone who can reach `/mcp` unauthenticated can call any exposed tool.
   Treat this port like you'd treat direct database access, not like a
   public API.

2. **Secrets handling**
   - `ALLEGRO_CLIENT_ID` / `ALLEGRO_CLIENT_SECRET`: never commit to
     `.env` files checked into git; use `.env` (gitignored — verify
     `.gitignore` covers it, add if missing) or your orchestrator's
     secret store (Docker Swarm secrets, k8s `Secret`, etc.) in
     production. File perms `600` if using a mounted `.env`.
   - `ALLEGRO_MCP_SERVER_TOKEN`: generate with
     `openssl rand -hex 32` (or equivalent); same handling as above.
     Rotate by changing the env var and recreating the container — no
     other state to clean up (the token is checked in-memory only, never
     written anywhere).
   - Today, **no credential or token is ever written to disk** by this
     process (the `token_path` config field is reserved for a future
     phase — see `src/config.rs`). The `allegro-mcp-tokens` named volume
     in `docker-compose.yml` currently only matters for an optional
     `allegro-mcp.toml` config file you may choose to mount there; it is
     forward-compatible with a future on-disk token cache, not load-
     bearing for security today.

3. **Network exposure**
   - Default posture: bind `0.0.0.0:8080` inside the container, but only
     publish the port to a private Docker network (e.g. the same compose
     network as Open WebUI) — **do not** publish `8080:8080` to a public
     interface without a reverse proxy in front doing TLS + auth.
   - `ALLEGRO_MCP_SERVER_TOKEN` is a defense-in-depth static-token guard,
     **not** a substitute for TLS — it's sent as a plain bearer header,
     so it must only traverse TLS-terminated or otherwise-trusted network
     segments (Docker-internal network, VPN, or behind a TLS-terminating
     reverse proxy).
   - `ALLEGRO_MCP_ALLOWED_HOSTS=*` disables the Streamable HTTP
     transport's DNS-rebinding protection — only use this if you already
     have equivalent protection upstream (reverse proxy enforcing
     `Host`), never on a directly-published port.

4. **Container hardening notes**
   - Runtime image is `gcr.io/distroless/cc-debian12` — no shell, no
     package manager, no `apt`, drastically reducing what an attacker
     with code execution inside the container can do next.
   - It runs as **root** (uid 0) today, to match the documented
     `/root/.config/allegro-mcp` volume path. If you need a non-root
     container for compliance reasons, switch to
     `gcr.io/distroless/cc-debian12:nonroot` in your own fork of the
     `Dockerfile` and update `HOME`/the volume mount path to
     `/home/nonroot/.config/allegro-mcp` accordingly — this is a
     straightforward follow-up, not attempted here to keep this phase's
     scope matching the issue.

5. **Revoking Allegro-side access** — if `ALLEGRO_CLIENT_SECRET` is
   compromised, or you're decommissioning a deployment: log into
   [apps.developer.allegro.pl](https://apps.developer.allegro.pl), find
   the application, and either regenerate its client secret or delete
   the app registration outright. From the *account* side, an Allegro
   user who authorized the app (for `authorization_code`/device-flow-
   based scopes, if ever added — see Section 0) can revoke it under
   **allegro.pl → Ustawienia → Aplikacje → Powiązane aplikacje**
   ("Settings → Applications → Linked applications") — revoking there
   invalidates any tokens issued under that authorization immediately.
   `client_credentials` app-tokens (what this server uses today) are
   tied to the app registration itself, not a per-user authorization, so
   secret rotation at the app-registration level is the relevant control
   for the current auth flow.

6. **Reporting a vulnerability** — standard boilerplate: email/contact
   method (ask the user for their preferred contact — GitHub Security
   Advisories on this repo is a reasonable default if nothing else is
   specified), response-time expectations, no public issue for
   undisclosed vulns.
